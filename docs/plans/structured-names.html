  • Server IdentityMirror: store handle → { name, terms }. Add searchTerms(address) (for conversation matching) and search(query, limit) (Convex-backed contact results).
  • /api/contacts: search the mirror's Convex terms, merged with ContactBook (Apple freshness), deduped — so "Uncle Jimmy" AND "Jimmy Sciandra" both return the contact.
  • ChatSummary gains searchNames?: string[] (participants' mirror terms); the palette conversation/group scorer matches against it → the conversation surfaces for any of the person's names.

CRM subjects: people AND chats (decided 2026-07-24)

The insight: a DM's priority IS the person's priority — giving DM chats their own would create two competing truths for one conversation. Groups have no single person, so they need their own. Hence:
  • Groups carry their own favorite / priority / tags / event links (chat_crm, keyed by chat guid, in Convex).
  • DMs inherit from the linked person — resolved in mapChat, never stored twice.
  • Stored in Convex, not the Overlay. The Overlay is deliberately ephemeral UI mechanics (archived-at, dismissal guids, mute); CRM is durable personal metadata that must survive a Mini rebuild and be browsable across people + chats in ONE index.
  • Priority = P1–P5, 1 = highest. Matches the Todoist mental model; explicitly NOT inverted like Todoist's own API (see root CLAUDE.md's warning).

  • Event/project association is a typed link to an Airtable Event record (id + cached name), on people and chats alike — Airtable stays the owner of event data, consistent with the three-owner rule. Freeform tags would have meant no deep-link and typo-fragmented projects.

MEMBERSHIP ≠ OWNERSHIP (the rule that protects privacy)

Neither Apple nor Airtable is a superset, and we deliberately don't make either one. Apple ≈ 1,518 personal contacts; Airtable ≈ 7,267 AUF community records (6,479 never talked to); only 788 overlap. Forcing either to be complete is actively harmful — personal contacts in a shared AUF business database is a privacy problem, and 6,479 strangers in your phone would wreck autocomplete.
  • Ownership decides where a field lives for people who exist in both. It says nothing about who should exist where.
  • Convex is the only superset — the union of Apple ∪ Airtable ∪ Beeper is precisely its job.
  • Sync NEVER creates a record in a source — update-only. The mirror image of the link_only rule already shipped on the read path. Consequence: personal contacts can never leak into Airtable — there's no record to update and we don't create one.
  • Promotion is explicit: an "Add to Apple Contacts" action in the person view for a Convex-only person who turns out to matter. One at a time, deliberate — never automatic (auto-creation is what produced the 6,433 phantom people earlier).

Key correction that unlocked this: "birthday can't come from Apple" and "organization has no source" were never real design constraints — they're artifacts of BlueBubbles' skinny 6-field contact API. Apple has both. Replacing that bridge (CardDAV, decided below) removes the special cases entirely.

Storage role then follows from ownership: projected (mirrored into Convex because the app displays/edits/resolves on it), Convex-native (Convex IS the record), or pass-through (lives in the source; app displays and edits it through, Convex needn't store).

Bidirectional sync topology (answering "can changes propagate both ways?")

Yes — and the hard part is already built. Two-way sync normally needs a per-source snapshot to answer "what changed since last time." The identities table IS that snapshot: 
identities[source=apple_contact].<field>    ← what we last saw from Apple
identities[source=airtable_human].<field>   ← what we last saw from Airtable
people.<field>                              ← canonical merged value
That's a three-way merge; change detection is a diff, requiring no vendor change-feed:
  • Source A's current value ≠ our stored A row → A changed → propagate to B, update both stored rows.
  • Both changed to different values between syncs → conflict → queue for review (rare enough to stay empty in practice; exists so it fails loudly instead of clobbering).
  • Loop prevention: when WE write to a source, immediately update that source's stored row to the value written. Next sync sees current == stored → "no change" → no echo. This is the classic gotcha; the ledger solves it.
Airtable has no Last Modified Time field on Humans today (standard field type, trivially addable) and offers a webhooks API — but neither is required, they're optimizations over polling+diff.

Proposed design (Phase 1 mechanics)

1 · Schema (additive, optional — no destructive migration)

identities: + first_name?, last_name?, nickname?   (per-source structured parts)
            + source_contact_id?  (Apple contact id — for Phase 3b write-back)
people:     + first_name?, last_name?, nickname?   (aggregated projected)
            + organization?                        (Convex-native, app-owned)
            display_name / display_name_locked stay (lock now guards ALL name fields)

All optional, so existing rows stay valid; structure fills in as syncs re-run. Apple's contact id is retained now so Phase 3 write-back can target the right source record (Airtable's is already stored as airtable_human_id).

2 · One "primary name identity" per person (coherence rule)

To keep display_name and first/last from disagreeing, recomputePersonAggregates picks a single primary identity by source priority — apple_contact > airtable_human > manual > beeper — and takes display_name, first_name, last_name all from it. Apple wins because it's already the canonical name source (consistent with the identity-mirror hierarchy). A locked person keeps its manually-set name regardless.

3 · display_name derivation

Per identity: display_name = the source's own display string (Apple displayName/nickname, Airtable Name) if present, else "First Last" from the parts, else the handle. This preserves good labels like "The Brooklyn Mirage" while still capturing first/last separately for sort.

4 · Ingest changes

  • identity-sync.ts (Apple): pass through firstName/lastName instead of discarding; keep the assembled display_name.
  • airtableSync.ts: add First Name/Last Name to FIELDS; map into the card.
  • ingestContacts.ts ContactCard + ingestOneCard: carry first_name/last_name onto the identity (respecting the no-op-write discipline already in place).
  • mutations.ts createPerson/renamePerson: accept first_name/last_name; a manual edit sets the parts, derives display_name, and locks all three.

5 · Client (Phase 1)

  • person-content.tsx edit UI: replace the single Name box with First, Last, Nickname, Organization, and a Display-name override (both rename + add-contact flows).
  • lib/identity.ts: thread first_name/last_name through the hand-typed refs + hooks (useCreatePerson, useRenamePerson), plus the shared-key arg.
  • contacts-list-pane.tsx: no change in Phase 1 — sort and display stay exactly as today. Last-name sort + "Last, First" is Phase 2, behind the settings toggle.
  • Chat headers / inbox names stay natural "First Last" (unchanged — they read display_name via the mirror).

6 · Backfill (no one-off migration script needed)

Fields are additive, so backfill is just re-running the syncs once they carry the new data: trigger an Apple identity-sync pass and an airtableSync run after deploy; recomputePersonAggregates then derives each person's first/last. Manually-locked names are preserved by the lock guard. Verify with internal:stats and a spot-check of a known contact.

Non-goals

  • Pushing edits back to Apple Contacts or Airtable (pending Q1).
  • Middle name / prefix / suffix / phonetic / organization fields — Apple has them, but out of scope; first/last covers the stated goals. Can extend later (additive).
  • Changing how inbox / chat-header names render (they stay "First Last" via display_name).
  • Heuristic parsing of any single-field name — unnecessary now that every source has real structured columns.
