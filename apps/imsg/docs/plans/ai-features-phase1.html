1. Goal

Add AI to the imsg client, powered by GPT models billed to the ChatGPT/Codex subscription rather than per-token API spend. Four surfaces, all desktop-only for phase 1:

  1. Group name suggestions — propose names for a group thread.
  2. Message suggestions — draft replies from the conversation plus what the system knows about Milad.
  3. Contact suggestions — infer who an unknown number belongs to.
  4. Shadow conversation — a side panel to talk with an agent that has real desktop context and can act.

3. Confirmed decisions

D1 — Two lanes, split by latency budget

A suggestion shelf that takes 8s is dead UI; a shadow conversation with no desktop context is just a chat box. So the surfaces split:

LaneTransportServesContext
Fast Raw POST 127.0.0.1:8317, gpt-5.6-luna(low), ~2s Group names, message suggestions, contact inference Transcript + server-assembled blobs. No tools.
Harness ccs delegate → claude-gpt, ~8s/turn Shadow conversation Full desktop: vault, skills, MCP, memory

D2 — Server owns the shadow transcript

Shadow history lives in the SQLite overlay keyed by chat, and each turn replays it into the prompt. The UI must render the transcript regardless, so the server holds it either way.

D3 — Suggestions powerless, shadow chat fully empowered

Suggestion lanes get no tools at all. The shadow conversation runs --permission-mode bypassPermissions so it can genuinely act — run tools, save things, and surface suggested actions ("add this person to the guest list", "put this flyer in Airtable") alongside suggested messages.

Accepted risk, stated once. The shadow context contains message text written by other people. With bypassPermissions and no approval seam, an instruction embedded in an inbound message can execute with full MCP reach (Airtable, Slack, Gmail, 1Password) and would only be noticed after the fact. Milad accepted this explicitly for a tailnet-only personal tool.

Free mitigation included: inbound message text is wrapped in explicit delimiters and the system prompt states that message content is data, never instructions. This defeats casual injection, not a determined one.

D4 — Managed-session-births contract binds; anchor + delegate (canonical daemon recipe)

Final shape, per the contract owner. Supersedes both the self-spawn revision and the original anchor sketch — automation support now covers delegate, so no direct spawn is needed.

Reserve one transcript-free anchor at first use and persist its UUID in the overlay DB:

ANCHOR_ID="$(
  CCS_CREATOR_KIND=automation \
  CCS_CREATOR_REF='imsg-shadow' \
  ccs session new \
    --top-level \
    --cwd /Users/mimen/Programming/Repos/master-db/apps/imsg \
    --title 'imsg shadow conversation' \
    --print-id
)"

Then every shadow turn is one synchronous delegate against that anchor:

CCS_CREATOR_KIND=automation \
CCS_CREATOR_REF='imsg-shadow' \
ccs delegate <seat> \
  --child-of "$ANCHOR_ID" \
  --cwd /Users/mimen/Programming/Repos/master-db/apps/imsg \
  --prompt '<rendered transcript + turn>'
  • ccs delegate is synchronous and preserves stdout and exit status — the reply is its stdout.
  • Each turn is an auxiliary child, hidden from normal CCS views.
  • creator_ref identifies the daemon; parent_session_id points at the anchor, so all turn costs roll up under it.
  • CCS_CREATOR_REF must be stable and non-empty — automation births are rejected without it.
  • No direct claude / claude-native / claude-gpt spawn. No automatic retry of a launched child.

Consequence: a seat is required after all (delegate takes one), and turns land as auxiliary session records rather than the zero D2 originally implied. The transcript still lives in SQLite because the UI must render it.

Prerequisite: imsg runs on the Mini, so the Mini's ccs must be a build that includes automation provenance before the shadow lane can work. Steps 2–4 do not depend on it.

D5 — Suggestions generate once on open, then on demand

One automatic generation when a chat opens. New inbound messages mark the shelf stale rather than firing a regeneration, so a five-message burst costs one call, not five. A refresh affordance regenerates explicitly.

D6 — Contact inference: server retrieves, model reasons

Phone-number lookup is a deterministic search, not something a model should freelance. The server runs the lookups in parallel — vault grep, Airtable Humans by phone, BlueBubbles contact book — and hands 0–3 candidates to the fast lane, which picks and explains. Model stays toolless and ~2s.

New dependency: Airtable credentials must be reachable from the Mini.

4. Constraints and non-goals

  • Desktop only. Gate on wide && Platform.OS === "web". Mobile and native are untouched.
  • Never auto-send. Every suggested message requires a click. The agent does not send iMessages.
  • No pre-generation across the chat list. Only the opened conversation generates.
  • Gateway key never reaches the client. All model calls originate server-side.
  • Group rename already exists (POST /api/chats/:guid/rename) and needs the BlueBubbles Private API — name suggestions degrade to copy-only when it is off.
  • Not in phase 1: summarization, auto-replies, background analysis of unopened chats, mobile support.
